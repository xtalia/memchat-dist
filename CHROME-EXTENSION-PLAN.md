# Memchat Chrome 8.9.0.4 — прямые запросы МойСклад

## Изменения

- Сверен проверенный Node fetch клиент, используемый для рабочих задач МойСклад. В background polling исправлен отличавшийся Accept на application/json;charset=utf-8, как в прямом клиенте и core. Регрессия доказана RED → GREEN; пагинация и строгая обработка неполноты сохранены.

- Удалён worker scheduler: общая FIFO, два активных слота, искусственные 500/625 мс между стартами, weighted budgets, shared cooldown, persisted leases и зависимость допуска HTTP от quota/session storage.
- Extension runtime обходит локальный scheduler неизменённого standalone userscript. Нужные задачи отправляются сразу после проверок актуальности ключа, без ожидания локального cap/cooldown. Сам standalone userscript, его generated-файл, src и DEV не менялись.
- Позиции выбранных документов читаются без пула на два документа; неполный или устаревший снимок всё ещё отклоняется целиком.
- Временный сбой MS GET/HEAD (сеть, таймаут, 408/429/5xx, API 1073) получает один повтор. Между попытками — 500 мс либо большая явная серверная Retry-After. Пауза относится только к неудачному запросу и не задерживает другие запросы/вкладки.
- Обычные ошибки 400/401/403/404/422 возвращаются без повторного запроса с теми же некорректными данными. POST/PUT/PATCH/DELETE автоматически не переигрываются после неоднозначного сбоя, чтобы не дублировать бизнес-операции.
- Старый memchatMsQuota_v1 не читается/не обновляется. После остановки worker новые запросы не ждут старые leases; старые операции не воспроизводятся.
- Сохранены приватное origin-scoped хранилище, каноническая проверка актуального Bearer перед каждой попыткой, отмена при смене/выключении ключа, allowlists/sender checks, Panel CSRF/session и единый профильный опрос заказов без дублирования вкладками.

## Проверки

- RED: новые регрессии до реализации воспроизвели ожидание старого бюджета, cap/паузы во вкладке и worker, fail-closed quota storage и отсутствие повторов после временных ошибок.
- Полный JS suite: 231 passed, 0 failed.
- Python updater suite: 32 tests, OK, 1 skipped.
- Packaged Chromium: основной smoke, orders-service, storage/restart, прямой MS transport и реальный Windows updater/reload прошли.
- Direct MS smoke: две реальные content-вкладки, пик шести одновременно активных fixture-запросов; 503/network успешно повторяются; синтетический POST и 401 не повторяются; Retry-After не блокирует другую вкладку; смена/выключение ключа отменяет старую работу; настоящий CDP stop/wake игнорирует старую квоту.
- Windows updater: загруженное расширение 8.9.0.2 → 8.9.0.4 по прежнему пути, реальная стрелка Reload, тот же extension ID, режим калькулятора и история сохранены/мигрированы.

## Границы

Исходный пользовательский сбой не воспроизведён на реальном аккаунте: выявлены и удалены механизмы локальной блокировки, но без HTTP-ответа пользователя нельзя установить конкретную причину его ошибки. Нагрузочные MS и authenticated Panel проверки синтетические; реальные бизнес-записи не выполнялись, секреты не копировались, не выводились и не включались в пакет. Отдельный контрольный GET через существующий прямой Node-клиент с его уже настроенной авторизацией успешно получил одну строку store; это не authenticated E2E расширения. Серверные ограничения МойСклад не отключаются, и отсутствие любых 429 не обещается. Нативный macOS не проверен.

## Обновление

Обычный Update-Memchat.cmd / Update-Memchat.command, затем Reload на карточке расширения и перезагрузка рабочих вкладок. Расширение не удалять и путь не менять: Chrome-owned данные сохраняются в прежнем профиле/ID. Папка backup содержит код, не приватные данные Chrome.
